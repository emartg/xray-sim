# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html) (before v1.0.0, minor versions may include breaking changes, and the releases are pre-releases).

## [Unreleased]

### Added

- Top-level CMake project (CMake 3.26, C++20) that builds the Engine and the core library of gVirtualXRay as subdirectories, with a `vcpkg.json` manifest pinned to the Engine's baseline, and CMake presets for Ninja with MSVC, Visual Studio 2022 and 2026, MinGW Makefiles with GCC (Windows), and Ninja with GCC or Clang (Linux), adapted from the Engine's.
- `XRSim`, a minimal application on top of the Engine (a window with a placeholder panel) with the `--frames N` command-line option, and the tests `XRSim_Smoke_Test` and `XRSim_Invalid_Argument_Test`.
- GitHub Actions CI: formatting check with clang-format 23.1.1, Linux builds (GCC Debug and Clang Release, with the tests under a virtual display), and Windows builds (MSVC and MinGW, with a vcpkg binary cache).
- gVirtualXRay, as a Git submodule of the fork, built as its core library alone (option `XRSIM_BUILD_XRAY`, off by default with MSVC), with the system packages on Linux and vcpkg packages on Windows (triplets `x64-windows-xray` and `x64-mingw-dynamic-xray`, which build GLEW as a static library, as the fork requires).
- `XRSim_Xray`, the library that adapts gVirtualXRay to the simulator (it links the library privately and does not expose its headers), with the class `Gvxr_Adapter` and the test `Gvxr_Adapter_Test`.
- Build instructions, the credits of the third-party libraries and resources (`docs/sources.md`), and the formatting configuration of the Engine (`.clang-format` and `.editorconfig`).
- The adapter computes X-ray images: `Gvxr_Adapter` owns the X-ray renderer, the beam, the detector, and the meshes, and computes the image of the meshes on the OpenGL context of the Engine's window, inside the Engine's frame. It saves the state of OpenGL, sets the defaults that the library relies on, and restores the state after each call, and its interface uses plain types (`Xray_Types.h`), without headers of the library or of the Engine. A workaround is needed to register the current context with the library, which cannot adopt an existing one (it goes away when the library provides a function for it).
- `--xray-self-test` option and `XRSim_Xray_Self_Test`: in the first frame, the simulator computes the X-ray image of a cube of water of 10 cm with a beam of 80 keV, and checks that the transmission is the one of the Beer-Lambert law (0.1593, within 3 percent) and that the state of OpenGL is unchanged.
- The scene library `XRSim_Scene`: a cube, a sphere, and a cylinder as closed surfaces with outward triangles, a table of materials (water, aluminium, iron, and bone), and the `Scene` class, with a default scene and the X-ray meshes of its objects in millimetres (the unit of a scene is the centimetre), and its test `Scene_Test`, which also runs in the Windows jobs of the CI.
- The Engine draws the default scene with its forward rendering (a camera, a directional light, and a node for each object, built by `Scene_Builder`), and a `Scene` window lists the objects.
- The X-ray image of the scene, next to the 3D view: `Xray_View` gives the meshes of the scene to gVirtualXRay once, computes the image of a point source and a flat detector (256 by 128 pixels of 2 mm, 80 keV) when the first frame is drawn and when the user presses the Recompute button, and shows it in an `X-ray` window. The `Single X-ray view` switch shows the image as the background of the whole window instead, and the scale (linear or logarithmic) and the negative can be chosen.
- The display library `XRSim_Display`: the conversion of an X-ray image to grey values, relative to the unattenuated beam (linear or logarithmic, optionally negative), with its test `Xray_Display_Test`.
- Controls of the X-ray setup in an `X-ray setup` window: the energy of the beam (20 to 150 keV), the distance of the source and of the detector to the scene, the size of a pixel, and the size of the detector in pixels. The image is computed again when a value changes (the option `Recompute on change`, with an `Apply` button when it is off, and a `Reset` button), and the window shows the magnification and the size of the detector. The setup is the new class `Xray_Setup` of the scene library, which converts the distances to the millimetres of the X-ray library and keeps every value within its limits (for example, the source cannot be inside of the scene), with its test `Xray_Setup_Test`.
- `--xray-view-test` option and `XRSim_Xray_View_Test`: in the first frame, the simulator checks that the corners of the X-ray image of the scene are not attenuated, that the beam is attenuated where each object projects, and that the iron sphere attenuates more than the water sphere. It also changes the setup, and checks that a lower energy attenuates more and that another geometry and detector give a valid image of the new size.
- The pin guard: CMake stops at configure time when `engine/` or `gvirtual-xray/` (when the X-ray part is on) is not at the commit that the repository records for it. The index is compared, so a new pin can be tried with `git add` before it is committed. The message names the folder, both commits, and the two ways out (`git submodule update <folder>`, or `git add <folder>` and a commit); the option `XRSIM_ALLOW_UNPINNED_SUBMODULES` turns the stop into a warning; and the check is skipped, with a status message, when Git is not available, the sources are not a Git checkout, or a submodule was not fetched. Its test, `Submodule_Pin_Guard_Test`, creates small Git repositories and runs the guard on them.
- Timers around the stages of the X-ray image: the adapter measures its state guard, its initialisation (the loading of the OpenGL functions and the renderer apart), the addition of the meshes, the computation (until the GPU has finished), and the read-back, and Xray_View measures the destruction of the previous adapter, the meshes of the scene, the mirror, the grey conversion, and the upload of the texture. Every change of the X-ray setup prints the times ([INFO::XRAY_VIEW::apply_setup] ...), and the X-ray setup window shows them with the number of images computed in the last five seconds and the frames per second. The --xray-self-test option checks that the times are valid.
- A `Troubleshooting` section in `docs/build_instructions.md` for the failures of a configuration or a build, with the entries of the pin guard (the routine to put the folders at the recorded commits and back, and the option that allows them), `Restored 0 package(s)` (what it means and how to find the cause), the lock and the inconsistent installed folder of vcpkg, a build folder that holds the tools of another compiler, `cl` not found, `VCPKG_ROOT` pointing to Visual Studio's own vcpkg, the gzip download of gVirtualXRay, and the crash at start-up when the Engine folder is at another commit.
- Picking and materials (step 4b of the prototype): a click on an object in the 3D view selects it (the Engine outlines it), and the `Scene` window highlights its row and shows its data (name, shape, X-ray compound and density, position, rotation, and scale) with a combo to change its material. The colour of the Engine's node takes the new material, and the X-ray image takes it in place and is computed again. `Scene` gets `set_object_material`, `remove_object`, and a revision that every change raises, and `Scene_Builder::build` returns the id of the node of each object. The new class `Scene_Sync` keeps the Engine's nodes and the scene in step: if the user deletes the selected node with the Delete key of the Engine, the object leaves the scene and the X-ray image. `Scene_Test` checks the changes of the scene, and the view test checks the change of a material, the deletion of a node, and the selection by a click at the centre of the 3D view.
- Controls of the objects (step 4c of the prototype, the objects): the `Scene` window has sliders for the position (-50 to 50 cm), the rotation (-180 to 180 degrees), and the scale (0.1 to 5) of the selected object, on each axis. The values are put within these limits, which only keep the scene valid, also when a value is typed. The node of the object moves, turns, and scales with it, and the X-ray image follows in place: `Gvxr_Adapter` now receives the meshes in their local space and moves them with a transform, which `Scene` provides. If the source or the centre of the detector ends up inside an object, no image is computed, the X-ray window says which object, and the last image stays until the object is moved away. `Scene_Test` checks the limits, the transform of the X-ray library against the world meshes, and the bounding spheres, and the view test checks the movement, the rotation, the scale, the refusal, and that the image updated in place is the one of a new adapter.
- A free X-ray tube (step 4c of the prototype, the tube): the `X-ray setup` window has sliders for the position of the source (-300 to 300 cm on each axis), the yaw and the pitch that point the beam (-180 to 180 and -89 to 89 degrees), the roll that turns the detector about the beam, and the source-to-detector distance (60 to 500 cm), and a button that aims the beam at the centre of the scene. The detector follows the beam: its centre is on the axis of the beam and it faces the source. `Xray_Setup` replaces its two distances on the axis z with these values, with the direction, the centre and the up vector of the detector, the projection of a point on the detector, and the magnification of a point; the default values give the same geometry and the same image as before. The source and the centre of the detector must stay outside of the objects, wherever the tube is. `Xray_Setup_Test` checks the free tube and the projection, and the view test checks that, with the tube beside and above the scene and the detector rolled, the shadow of each object is where the projection puts it, and that the image updated in place is the one of a new adapter. The limits only keep the geometry valid and carry no clinical meaning.

### Changed

- The X-ray part (gVirtualXRay and its adapter, option `XRSIM_BUILD_XRAY`) is on by default with MSVC too: the pinned gVXR force-includes its MinGW fix header only with MinGW, so MSVC compiles its library whole. The Ninja presets (Debug and Release) and the Visual Studio 2026 preset configure, build, and pass the nine tests, with the adapter test and the X-ray smoke tests, and the Windows MSVC job of the CI builds the X-ray part and runs the adapter test with the other tests that need no display. The Troubleshooting section has two more entries: the tools that the summary of vcpkg shows can differ from the ones of the runner, and the tests open a window of the desktop in WSL.
- The simulator is built as C++23 (`CMAKE_CXX_STANDARD 23`), the standard of gVirtualXRay and of the Engine, and requires CMake `3.26...4.2` (the range of gVirtualXRay and of the Engine; 3.26 is the minimum, as before, and the minimum of the presets is 3.26 too). The adapter library is no longer the only target at C++23, so the comments that explained that split are gone; the adapter keeps its isolation (its header includes no header of gVirtualXRay or of the Engine), which is about the two OpenGL loaders, GLAD and GLEW, and not about the standard. The Engine does not set a standard when it is not the top-level project, so its targets, which ask for C++20 as a minimum, are compiled as C++23 too.
- The message of the pin guard says that it is expected whenever a submodule folder is on one of its branches, and how to put the folder back on its branch after building at the recorded commit; its test checks the new lines.
- The README describes the current state of the prototype (the scene drawn by the engine, the X-ray image of the scene, the controls of the X-ray setup, the pin check, and what comes next) and the structure of `src/`, `tests/`, and `cmake/`.
- The pointer of the gVirtualXRay submodule moves to the latest commit of the fork, which has: the function `Context::adoptCurrentContext()`, to use the OpenGL context of the application (the simulator still uses its workaround, until a later change); the include of its MinGW fix header only with MinGW, which the MSVC build needs; the coverage flags of its Debug build as an option that is off by default; and changes of its own continuous integration. The Engine stays at v0.9.0.
- The pointer of the gVirtualXRay submodule moves to the latest commit of gVXR, which builds the two widget spheres of its detector with 3 subdivisions instead of 10 (21 million triangles each). Creating the objects of an X-ray image took 1.2 s in a Release build and 3.7 s in Debug, and now takes less than a millisecond, so an image of the X-ray setup (a new adapter, the meshes, and the computation) takes about 15 ms in Release and 18 ms in Debug for a detector of 256 by 128 pixels, and about 40 ms and 130 ms for 512 by 512. The same commit of gVXR has a `docs/` folder with its credits file, `docs/sources.md` (it was `doc/SOURCES.md`), and the links of the README and of `docs/sources.md` to it name the new path.
- The texts of the `XRSim`, `X-ray`, and `X-ray setup` windows wrap at the edge of the window, so a long line is no longer cut when the window is narrow, at the start or after the user resizes it. The times that every image prints to the console are an option now: the checkbox `Print the times to the console` of the `X-ray setup` window, off at the start (the times stay in the window, and `--xray-view-test` turns the option on).
- The pointer of the gVirtualXRay submodule moves to the latest commit of gVXR, which has documentation and diagrams only: its build instructions moved from `BUILD.md` to `docs/build_instructions.md` with a Troubleshooting section, its first diagrams (`docs/diagrams/`) with a check that each image has its source, and the workflow that runs the check. The code of gVXR is unchanged, and the Engine stays at v0.9.0.
- The simulator no longer links the coverage runtime of the Debug configuration on Linux (`--coverage` on `XRSim_Xray`): gVXR compiles its Debug build with coverage only when its option `gVXR_COVERAGE` is on (off by default since gVXR `88b8985`), and then its target adds the link option itself. The Debug builds with GCC 13, GCC 15, and Clang 21 configure, build, and pass the nine tests without the line, and no coverage flag appears in any compile or link command.
- `Gvxr_Adapter` uses `Context::adoptCurrentContext()` of gVirtualXRay to take the OpenGL context of the Engine's window, in place of the workaround that made the private readiness flag of the library's context public with `#define private public` (and of the call to `glewInit()` of the adapter, which the library now makes): the workaround is deleted, and the adapter releases the library's context while the context of the window is still current. The X-ray image of the self-test is the same (transmission 0.1594)
- The X-ray view keeps one adapter between the images and updates the beam and the detector in place, so a change of the energy, of the distances, or of the pixel size no longer creates a new renderer: an image of 256 by 128 pixels takes 4 to 6 ms in Release (7 to 9 ms in Debug) instead of 22 to 27 ms (32 to 38 ms in Debug). A change of the number of pixels, or a failed adapter, creates a new one. `Gvxr_Adapter` gets `update_beam`, `update_detector`, `set_mesh_transform`, `set_mesh_material`, and `reset_timings`, and holds its meshes through nodes of the library that it owns, so that their transforms and materials can change without rebuilding them. The `X-ray setup` window and the console line say whether the image came from an update in place, and the self-test and the view test check that the updates in place give the image of a new adapter.

### Fixed

- Windows: vcpkg built every package again on each configuration in the CI, and on a developer's machine whenever the `PATH` differed, because the MinGW triplet of vcpkg puts the `PATH` in the hash of the packages, and the hash of the tools of vcpkg depends on the build of `cl.exe`. The MinGW triplet of the repository (`x64-mingw-dynamic-xray`) keeps the `PATH` out of the hash (the first configuration after updating builds the packages once more), the CI uses the new host triplet `x64-windows-ci` (also without the compiler in the hash) with its CI triplets for the target, the key of the cache has the versions of CMake and PowerShell of the runner (the hash of every package has them too), and the summary of each Windows job shows how many packages were restored and the entries of the hash of `zlib` and `vcpkg-cmake`. Measured on a developer's machine: a configuration in another build folder (and, with MinGW, with another `PATH`) restored all 39 packages from the cache in 23 seconds with MinGW and 12 seconds with MSVC, instead of building them for 14 and 7 minutes.
- The Windows jobs of the CI use their vcpkg binary cache when GitHub moves a job to another build of the runner image: the CI triplets leave the compiler out of the ABI hash of the packages.
- The Windows jobs of the CI ran only some of the unit tests: they also run `Xray_Setup_Test`, `Xray_Display_Test`, and `Submodule_Pin_Guard_Test` now.
- The messages of the command-line check of `main.cpp` have the tag of the Engine's format (`[ERROR::MAIN::parse_command_line]`): a free function uses the name of its file in capitals as the class part.
- The links to the credits file of the Engine (`README.md` and `docs/sources.md`) point to its page on GitHub: the pinned v0.9.0 has no `docs/sources.md` (it came with a later commit), so the relative link led nowhere. They go back to the relative path when the pin reaches an Engine release that has the file.
- With the Visual Studio generators, the target that copies the DLL of xraylib beside the executables (`XRSim_Xraylib_Dll`) copied it to the folder of the configuration (`bin/Debug`) before that folder existed, which created a file with that name and made the build fail with `MSB3191`; the target creates the folder first. The Ninja and MinGW builds did not show it, because the folder already existed.
